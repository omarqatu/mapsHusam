## 1. Backend (`server.js`, 4.5 k lines, one file)

### Critical / high — fix before the public launch

| # | Finding | Evidence | Status |
| --- | --- | --- | --- |
| B1 | **One public request freezes the whole server.** `conditions_count` drives a synchronous loop with no cap. `GET /api/search-features?…&conditions_count=300000000` made `/healthz` time out for 50 s+ (site, sockets, everything). | `server.js:2006` | ✅ **Fixed** (cap 30, `Server changes`), live test added |
| B2 | **`/save-stat` is public and takes `user_id` from the body.** Anyone can add stats rows for any user id; each row counts against that user's quota, so an attacker can lock any user or provider out of contacting people, and inflate the "visits". | `server.js:1415-1440`, `checkUserRequestQuota` | ✅ code read. | B3 | **Fake "completed" requests can be rated.** `log-contact-click` inserts a `status='completed'` request for any `(service_layer, feature_id)` (no `isValidLayer`; with no linked provider the provider becomes the caller himself), and ratings only need a completed request of your own. Unlimited fake 5★ / 1★. Rating check is SELECT-then-INSERT (race, no unique constraint in the repo). | `server.js` `log-contact-click` (~4059), ratings (~3767) | ✅ insertion side read; 📄 rating side |
| B4 | **Proxy layer whitelist is bypassable.** Only `typeName/typename/TYPENAME/layers/LAYERS` are checked. `TypeName=`, `typeNames=` (WFS 2.0), `Layers=`, `query_layers`, `sld=` (GeoServer fetches a URL: SSRF), `cql_filter`, `/ows` paths pass. `typeName=x` → 403 but `TypeName=x` / `typeNames=x` reach GeoServer (400 from GeoServer). | `server.js:1264-1287` | ✅ measured on the dev server |
| B5 | **Public search returns `SELECT *`** and `get-unique-values` / `contains` accept any identifier-shaped column; `workspace` and `filter_*` are not validated. | B6 | **Login lockout can be used to lock out anyone** (10 failures per phone, no IP component, in-memory); `authLimiter` is one bucket for register / login / change-password and IPs are shared behind carrier NAT; 6-character passwords; legacy plaintext accounts still exist. | `server.js:170-192, 1750-1790` | 📄 |
| B7 | **Unhandled errors are swallowed** (`unhandledRejection` / `uncaughtException` only log); several async handlers have no try/catch (Express 4 does not catch them) → hung requests, process left in an undefined state and never restarted by nssm. | `server.js:4553-4558`, ratings, `check-request-limit` | 📄 |
| B8 | **Schema DDL runs at every boot, unawaited** (`ensure*` → `ALTER TABLE …`), server accepts traffic before it finishes, takes ACCESS EXCLUSIVE locks on `users` at every restart; some `ALTER`s target tables that no longer exist. `service_requests` has no unique index although the code relies on error 23505. | `server.js:327-458` | 📄 |
| B9 | **Production misconfiguration is silent:** CORS and socket.io fall back to allow-all without `ALLOWED_ORIGINS` (`origin.includes('localhost')` is bypassable); JWT secret falls back to a random key (every restart logs everyone out); `IS_PROD` depends on `NODE_ENV` (else DB error text is returned to clients); GeoServer default target is a hard-coded raw IP over plain HTTP. | `server.js:36-44, 81-88, 221-224, 2` | 📄 |

### Medium / low (📄 unless marked)

- `platform-stats` cache is keyed by client input (`excludedLayers`) → unbounded memory + DB load. Compute once, filter in memory.
- Polling endpoints do DB work per request (`/api/widgets-data` 3 queries, no cache; `/api/platform-content` 140 KB, no ETag). 1000 open tickers ≈ 50 queries/s on a remote DB.
- Caches and rate-limit state are process-local (works only as a single process); `connectedUsers` keeps one socket per user (second tab replaces the first) → use socket.io rooms.
- Search: up to 2000 unpaginated `SELECT *` rows, `rating DESC` puts NULL first, `ILIKE '%x%'` with `translate()` is a sequential scan.
- External HTTP in the request path with no single-flight (market rates, fuel prices); `?fresh=1` has no limit.
- `send_notification` (socket): unvalidated ids, unbounded lengths, N sequential INSERTs for "all users"; sockets survive a force-logout.
- No admin audit trail; view-session tokens not revocable; 201 `console.*` calls logging bodies and phone numbers.
- Missing indexes (inferred, check with `EXPLAIN`): `service_all(discriminator,status,auto_status)`, `map_service_stats(user_identifier,request_date)`, `service_requests(user_id|provider_user_id|status)`, `notifications(user_id,created_at)`, `service_ratings(provider_user_id)`, `users(phone)` unique.
- Data model: `TIMESTAMP` without zone everywhere (the widgets fix is a workaround), no FKs on requests / stats / `users.feature_id`, `rating` compared as text, no CHECK on ratings, `service_layer` stored in three forms.
- Dead legacy admin endpoints that expose every phone number (`/api/users`, `/api/stats-*`, …) — delete.
- `/healthz` checks one pool and the deploy smoke test hits `/` not `/healthz`; graceful shutdown is unreliable under nssm.
- CI only runs `node --check server.js`: no test covers auth, IDOR, quotas or the search SQL builder.

### Module split (no URL / method / auth / response change, one slice per commit)

`config/{env,layers}` → `db/{pools,migrate}` (awaited, numbered SQL, `schema_migrations`) → `middleware/{auth,limits,security}`
(`asyncH` wrapper) → `routes/{auth,search,stats,live,proxy,serviceRequests,admin}` → `services/{searchQuery,quota,notify,marketData}`
→ `socket.js`. Start with `searchQuery.js` and `auth.js`: most risk, easiest to unit-test.

## 2. Architecture — making the platform dynamic

**What already exists:** `features/visibility` (`settings.visibility`: hide layers / sections), `features/text-overrides`
(`settings.texts`: reword interface lines), `features/admin-texts` (legal texts, rows `legal.<key>`), all on one server table
(`platform_content`). Each has its own store; the next ones would copy ~80 lines each.

### Target

```
web/src/
  domain/services/   registry defaults, targets, groups (pure: no React, no OpenLayers)
  settings/          defineSetting({key, defaults, parse}) → use() / get() / useSave(); one prefetch of all settings;
                     generic admin page that renders a form from a field descriptor
  features/*         import only domain/, settings/, components/, api/
```

Rules: compiled defaults always present and the app renders from them (+ a `localStorage` mirror) before the server answers;
`parse` never throws (unknown / invalid fields dropped); a setting never holds a secret (`GET /api/platform-content/:key` is
public); anything the server enforces stays in code.

### Structure problems (📄 unless marked)

- `features/map/{registry,targets,config}` is a shared domain living inside a feature: 17 files in `home`, `widgets`, `requests`, `admin-*` import `features/map/*`; `components/UserMenu.tsx`, `AppHeader.tsx` import features; `visibility` imports the map. Move to `domain/`, add an ESLint `no-restricted-imports` boundary rule.
- One global `ErrorBoundary`: a map crash takes the shell down. Add boundaries around `MapPage` and each admin page.
- Files > 400 lines: `EditPanel.tsx` (623), `widgets/model.ts` (542), `StatusPanel.tsx` (495), `services.ts` (data).
- Map: `MapView` refreshes **every** visible data layer every 60 s for every visitor (≈ N layers × visitors requests per minute through the proxy); refresh only live layers (fuel, barriers), pause when `document.hidden`, and cache `/geoserver-proxy` GETs 5-10 s. WFS `maxFeatures` is not set by the map layer. `useVisibilityStore.subscribe(() => applyUi())` restyles the whole map on any change.
- Bundle: routes are lazy; `MapPage` chunk 431 KB + entry 343 KB (uncompressed); `vite.config.ts` has no `manualChunks`; check with a visualizer that OpenLayers stays out of the landing / home chunks. Confirm gzip / brotli on `/assets`.
- PWA: `sw.js` caches nothing by design → every visit is a cold load; cache the hashed shell (stale-while-revalidate) and the last good widgets data; keep API and map network-only.
- Tests: no e2e for the edit flow, requests / chat, notifications, legal; no test with a broken settings payload. CI has no `format:check`, no e2e job, no bundle budget, no dependency-boundary check.

### Migration order

1. Extract `domain/services`, ESLint boundary rule, per-route error boundaries (no behaviour change; unblocks the rest).
2. Generic `settings` module; migrate `visibility` and `text-overrides` onto it (their tests are the safety net); add `settings.site`.
3. Registry overlay; reduce map polling and add proxy caching in the same step.

## 3. Product — what would repel users, what would set the platform apart

Reviewed from a first-time visitor on a mid-range Android phone on 3G / 4G, in Arabic. 📄 (reading, no run) unless marked.

### What would repel users, ranked

1. **Sharing and search engines cannot see anything.** `web/index.html` has one static title, no description, no `og:*`; no `robots.txt`, no `sitemap.xml`; the server answers every route with the same `index.html`; there is no per-listing URL. A link shared on WhatsApp (this market's main channel) previews blank; Google indexes one page.
2. **Heavy first load on 3G:** `MapPage` 431 KB + entry 343 KB (+ `globalSearch` 202 KB, uncompressed), 17 promo images (~1 MB), satellite basemap by default, repeated WFS bbox downloads on pan, service worker caches nothing.
3. **Unmeasured funnel:** contact clicks by visitors are not logged (`useContactActions`: no user → nothing sent; `/api/log-map-event` needs a session). Sessions, zero-result searches, share clicks, installs, referrers are not measured at all.
4. **Sparse categories are a dead end:** the empty state only says "no matching results". No nearby area, related category, "tell us what you need", "add your business".
5. **Few trust signals:** no "last updated", no listing expiry or de-ranking of stale rows, no verified badge, no report button; new providers have zero ratings; the public ratings endpoint returns raters' full names.
6. **Supply and moderation are undefined:** registration forces `role='user'`; providers exist only when an admin promotes a user and links a feature; the only way to add a listing is admin map editing. No self-service "add my business", no approval queue, no claim flow. Sparse supply is structural.
7. **Privacy / abuse:** provider phone and WhatsApp numbers are public and scrapable (WFS + search) with no consent record; registration has no OTP (bulk fake accounts; fake requests; collusive ratings — see B3).
8. Login walls are small (map and `/search` are public; `/home`, requests, notifications need an account) but the register step asks a mobile number, a password and a Facebook "like" and never verifies the number.

### What already sets it apart, and what would deepen it

| Feature | Status | Effort | Impact |
| --- | --- | --- | --- |
| Live road checkpoints and fuel status, live prices ticker, `/widgets/portal` | exists | S polish | **Very high** — nobody else has it; a reason to come back daily |
| WhatsApp-first contact with a prefilled Arabic greeting | exists | S (add a WhatsApp *share* button on cards) | High |
| Shareable listing / location link **with a preview** | missing (location link exists, no preview) | M (same work as repel #1) | **Very high** — the viral loop |
| "Last verified" + owner-editable open / closed | missing | S–M | High — the trust moat |
| Map + list dual view | exists | done | Medium (link each view to the other) |

| PWA install + offline shell / last-good widgets | partial | S–M | Medium — checkpoint data offline is a real edge |
| Arabic-native UX | exists | — | table stakes, not a moat |

### Launch risks beyond code

- **Data quality:** everything depends on admin-entered GeoServer rows. Audit phones, duplicates, missing names per layer before launch; one dead number kills trust in a category.
- **Cold start:** no submission flow, so supply must be seeded. Pick one city and 2-3 categories with at least ~15 verified listings each; hide the rest with the show & hide page ("coming soon").
- **Support and moderation:** no support channel or "report a problem"; put a WhatsApp business number in the footer and legal texts.
- **Week-1 measures:** visit → search / map-open rate; contact clicks per visit (anonymous included); zero-result searches by category; register start → complete; median LCP on 4G; shares sent; widgets return rate on day 2 and 7.
- **Staged launch:** private beta (20-50 people via WhatsApp groups, one city, 2-3 categories) → add widgets and checkpoint status as the hook → widen categories only when each has ≥ 15 listings.

## 4. Recommended sequence (our synthesis)

**A. Safe to expose (days).** B1 ✅ done. Then B2, B3, B4, B5, B7 (`asyncH` + exit on uncaught), B9 (refuse to start in production without `JWT_SECRET`, `ALLOWED_ORIGINS`, `NODE_ENV`), B6 (lockout by phone + IP, separate limiters), the missing indexes and the `service_requests` unique index. Each its own commit + `Server changes` entry + a real-server test.

**B. Worth sharing (a week).** Server-injected meta + `og:image` for `/`, `/search`, `/legal/*`; `robots.txt` + `sitemap.xml`; a per-listing URL (`/l/:layer/:id`) with a preview; "last updated" on cards; empty-state ladder; anonymous event endpoint (rate-limited, hashed IP) for contacts, zero results, shares; lighter first load (chunking, first hero image only, lighter default basemap); report button + support number.

**C. Dynamic (in parallel, low risk).** Architecture §2 steps 1-3.

**D. Before the public announcement.** Data audit + one-city seed, OTP or CAPTCHA on registration, real-phone pass and production pass (already open in PLAN Phase 4), monitoring on `/healthz`, a rollback for admin visibility / text changes (the setting rows have no history).

## 5. Decisions needed from the owner

1. **B2 `/save-stat`:** require the session token and take the user from it; visitors' events are stored without a user and never count against a quota. This changes what "visits" means in the dashboard. OK?
2. **B3 ratings:** stop writing call / WhatsApp taps as `completed` requests (they would stay as events) and make rating need a confirmed request. Existing ratings built on such rows would stay but stop growing. OK?
3. **Supply model:** self-service "add my business" with admin approval (needs a pending state, a form, a queue) — before or after launch?
4. **Launch scope:** one city + a few categories first (recommended), or everything?
5. **Sharing:** approve server-side meta injection and a per-listing URL (a new public route; the SPA stays as is).
